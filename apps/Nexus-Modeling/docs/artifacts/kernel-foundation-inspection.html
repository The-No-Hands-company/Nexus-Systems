The bedrock is sound.
The build flags were not.

A first-principles review of every foundation layer against Parasolid, ACIS, OCCT, Blender, Houdini and Maya — asking only what is measurably true. The kernel's breadth is real and its geometry testing is genuinely thorough. The audit found that one compiler flag silently un-did the exact-arithmetic bedrock everything else is built on — since fixed and guarded — and four architectural decisions that will cap how far this can go before they are revisited.

§1

The one that had to be fixed first — now fixed

F1Critical

-ffast-math silently de-exacts the exact predicates

Resolved — commit 74bce163

-ffast-math dropped, -march=native replaced with a probed -march=x86-64-v2 baseline, -ffp-contract=off added. The exactness battery now carries an __int128 reference past 253 plus the recorded failing quadruple, and re-adding the flag fails it while all eight pre-existing batteries still pass — which is the proof they were structurally blind to it. The two dead std::isfinite guards were switched to their files' own bit-inspecting helper and pinned. Cost: ctest 34.4s → 34.8s. The finding is left in full below, because the way it hid is the reusable part.

The kernel builds with -O2 -march=native -ffast-math. Under -ffast-math, GCC is licensed to reassociate floating-point arithmetic — and Shewchuk's error-free transformations exist only as unreassociatable expressions. twoSum's error term is algebraically zero; a reassociating compiler folds it to literal zero. Which is exactly what happens: 

g++ -O2                          twoSum lo = 8.67e-19   ERROR TERM SURVIVES
g++ -O2 -ffast-math -march=native  twoSum lo = 0          *** FOLDED TO ZERO ***
g++ -O3 -ffast-math -march=native  twoSum lo = 0          *** FOLDED TO ZERO ***

With every error term zero, the expansion arithmetic degenerates to plain double. So the question is whether that still gets signs right. It does not. Running the shipping RobustPredicates::orient3D against an exact __int128 reference on integer-valued float coordinates:

Build of RobustPredicates.cppCasesExactly degenerateWrong signs
Project's real flags5,67596
Identical, minus -ffast-math400,0005370

The failure mode is the worst available: for points that are exactly coplanar the predicate returns a confident non-zero sign (measured -512, +128, -1024, +2048). It never returns zero, so the Simulation-of-Simplicity tie-break — the entire degeneracy strategy, and the thing pointPlaneSideSoS and segmentCrossesTriangleSoS are built on — never fires. Two thirds of exactly-degenerate configurations were decided by a coin flip.

Why the 1.2M-case exactness test passes anyway

The test bounds coordinates so its own reference stays computable in int64 — orient3D coords ≤ 215, determinant ≤ 251. That ceiling is below double's 53-bit mantissa, so plain double is also exact there. The bound chosen to make the reference exact is the same bound that makes the subject's inexactness invisible. Raising coordinates to 221 — still well inside float — pushes intermediates past 263 and the failures appear immediately.

This is the second time this bedrock has been certified by reading rather than measuring at the boundary. The first time (inc69) the algorithm was wrong. This time the algorithm is right and the build destroys it.

Two further consequences of the same flag, both live: std::isfinite returns true for NaN and Inf under these flags, so the non-finite guards at render/Camera.cpp:113 and sim/FluidSolver.cpp:215 are dead code — NaN passes straight into the view matrix. (The geometry module is immune: its own geometry::isFinite inspects the IEEE exponent bits.) And -march=native bakes host CPU features into the binary, so FMA contraction differs per machine — which contradicts the kernel's stated cross-machine determinism invariant and makes the release binary non-portable.

FixDrop -ffast-math; replace -march=native with a baseline ISA. Add -ffp-contract=off for the predicate translation unit.
Verified400,000 cases / 537 exact degeneracies / 0 wrong signs with the flag removed. Ready to apply.

Then widen the exactness test to a coordinate range where double cannot be exact (__int128 reference), so this can never be re-certified by a test that cannot see the failure.

§2

Four structural decisions that cap the ceiling

None of these is a bug. Each is a design choice that is correct for where the kernel is and wrong for where it is going, and each gets more expensive to change with every feature layered on top. They are the ones to decide deliberately now.

F2Structural

No attribute system — every extra datum needs its own side-car

MeshAttributes has six fixed slots: positions, normals, tangents, one UV set, joint indices, joint weights. There is no named-attribute facility anywhere in the public API — no domains, no interpolation rules, no custom channels. That single decision is upstream of a long list of missing capabilities: multiple UV maps, vertex colour layers, per-face material indices, sharp/seam/bevel-weight flags, vertex groups, face maps, and any user- or node-authored data.

The symptom is already visible. Subdivision creases live in a CreaseEdgeSet — a side-car unordered_map keyed by vertex-index pairs, passed in as an option. It is not stored on the mesh, so it cannot be serialized with it, cannot be painted, and does not survive any topology edit that renumbers vertices. That is what happens to every attribute in a fixed-slot design: it becomes someone's parallel array with its own lifetime bug.

Industry standardBlender CustomData / attributes; Houdini point-prim-vertex-detail attributes; USD primvars. Typed, named, per-domain, with declared interpolation.
Why it is the #1 architectural gapGeometry nodes, modifiers, shading and interchange all read this layer. It cannot be retrofitted cheaply once 120 ops hardcode the six slots.
F3Structural

The kernel is entirely single-threaded

Zero std::thread, zero std::async, no std::execution policies, no OpenMP, no job system or thread pool — across all 72,339 lines. Two documented claims of parallelism do not exist in the code: MeshBVH's "parallel build" is serial, and the "parallel solver parallelSolve" is not in the tree at all (the word refers to the geometric parallel constraint).

Every competitor parallelises the things this kernel does serially: BVH construction, subdivision, boolean classification, remeshing, sculpt brush application over BVH nodes, modifier-stack evaluation, and dependency-graph evaluation. On a 16-core workstation the kernel currently leaves roughly 94% of the machine idle. "Better, stronger, faster" is not reachable from a single thread.

Sequencing note

This is deliberately second, not first. Parallelising code whose predicates are non-exact multiplies non-determinism; and a task system introduced before the attribute layer will need reworking when data ownership changes. Fix F1, decide F2, then build one task system and convert the measured hot spots — not fifty ad-hoc threads.

F4Structural

Single-precision coordinates cap achievable accuracy at ~1e-6 relative

Vec3 is three floats, and every mesh, B-rep vertex, surface and curve stores float. The Tolerance model is well built for float — kDefaultRelative = 1e-6 is about 8 ULP at unit scale, which is the right choice — but it also states the ceiling: roughly six usable decimal digits of geometry. A part 1 km across resolves to about 0.06 mm and no finer, and cannot carry a 1 µm feature at all.

Industry standardParasolid, ACIS, OCCT and Rhino are double throughout (~1e-15 relative). Blender stores mesh coordinates as float but computes booleans in double/exact.
Consequence if unchangedFine for DCC-scale polygon work. Not enough for the CAD half of the north star — the B-rep exists to compete with Plasticity and Rhino, and those users model at ratios float cannot hold.

Note the interaction with F1: the exact predicates were deliberately written to be exact for arbitrary double input, so the predicate layer is already ready for this migration. The cost is in the 121 geometry sources and the serialized formats, and it only grows.

F5Structural

The half-edge core is manifold-only; DCC editing lives in non-manifold states

HalfEdgeMesh enforces manifoldness and rejects non-manifold input — correct and valuable for the Euler operators and the watertight guarantees built on them. But polygon modelling passes through non-manifold configurations constantly: wire edges, isolated vertices, three faces on one edge mid-operation, a bowtie the user is about to fix. Blender's BMesh is explicitly non-manifold-tolerant precisely so an artist can be halfway through a bad edit without the kernel refusing to represent it.

The right answer is probably not to weaken the manifold core — it is what makes the B-rep provable. It is to be explicit that there are two topology tiers (a tolerant editing tier and a validated solid tier) with a defined promotion path, rather than leaving the tolerant tier absent and the editing ops routed around a structure that will not hold their intermediate states.

§3

Where the breadth is thinner than the header list suggests

122 geometry headers is genuine breadth, and 121 of 121 geometry sources are referenced by tests — that discipline is real and rare. These are the places where a capability exists as an entry point but not yet at industry depth. Listed so the map matches the territory.

F6Depth

The B-rep boolean knows four surface pairs

Substantially addressed — 2026-08-02

The pairwise table is now eleven pairs, not four: plane∩{plane, sphere, cylinder, cone}, sphere∩sphere, cylinder∩cylinder (the two-pipes case called out below), sphere∩cylinder, and the three cone pairs cone∩{cylinder, sphere, cone} added in commit 8c4a9832.

The cone's absence was worse than a missing feature. imprintOneWay handled Unsupported in the same switch arm as None — “nothing to imprint” — and then reported success, so the imprint did no work on interpenetrating solids and the watertight-or-empty invariant turned that into a clean-looking empty body. A cone unioned with a coaxial rod returned EMPTY at every offset tried, and nothing anywhere recorded a problem. booleanToBody now carries a BooleanDiagnostic (bb6408f4) so an empty result says whether it is a correct answer, a missing capability, or a failed sew.

That diagnostic then re-ordered this section's priorities. Measured over 3,592 chained boolean steps: 53.0% Ok, 35.2% declined for an inexpressible seam, 6.9% sew failures, 4.9% legitimately empty. The absent curved intersection was about five times the next-largest gap — the opposite of how the two had been ranked.

A numerical tracer for the remaining quartics landed in a6191fe0 (BRepSurfaceTrace.cpp): Newton projection onto both surfaces, marching along ∇a×∇b with adaptive sag control, tangent-continuity detection at singular points, and rejection of tangency debris — verified against the closed forms it must reproduce and against the Steinmetz identity, bitwise deterministic, sub-millisecond. It is not yet wired into the imprint: it yields polylines and the B-rep stores analytic curves, and joining them is a representation question still open.

Unchanged below: fillet depth, and the absence of STEP/IGES.

intersectSurfaces handles plane∩plane, plane∩sphere, plane∩cylinder and sphere∩sphere. Everything else returns Unsupported, which means the analytic boolean cannot cut cylinder∩cylinder (two pipes — arguably the most common real CAD intersection), any cone, any torus, or any NURBS face. A general SurfaceSurfaceIntersect exists but is 247 lines of marching that returns loose Vec3 polylines with no topology, no (u,v) traces, and no singularity or branch handling — and it is not wired into the boolean at all.

Related: the fillet family is MeshFillet 186 lines, FaceFillet 209, SurfaceBlending 161. Real B-rep blending — rolling-ball surfaces, G1/G2 continuity, variable radius, vertex blends with setback, blend-blend intersections — is one of the largest modules in any commercial kernel. And there is no STEP or IGES I/O, so the B-rep cannot exchange with the CAD world it is built to compete in.

F7Depth

Voxel and SDF are dense grids

MeshVoxelize and MeshSignedDistanceField both key off std::array<uint32_t,3> resolution with a flat z*w*h + y*w + x index — dense allocation, default 32³. At 512³ that is 134M cells; at 1024³ it is multi-gigabyte for a surface that occupies a few percent of the volume. Sculpt-scale SDF work is not reachable this way. The industry answer is a sparse hierarchy (OpenVDB, which is what Blender's voxel remesh and all of Houdini's volume work use).

F8Depth

Sculpt has no multiresolution and no dynamic topology

SculptSession has strokes, a per-vertex mask and brushes — a correct foundation. What is missing is what makes sculpting usable: multiresolution levels (sculpt at 10M+ vertices, edit at 10k), dynamic topology (local remesh during the stroke), sculpt layers, and a paint-BVH for partial redraw. Without these, the brush works and the workflow does not scale past a low-poly cage.

F9Depth

Instancing bakes geometry; the scene graph has no instances or LOD

MeshInstancer::scatter returns a single merged Mesh. Scattering 10,000 trees allocates 10,000 copies of the tree. There is no per-instance transform path, no GPU instanced draw, and no LOD in SceneGraph (frustum culling is there). Every competitor represents instances by reference — Blender dupli/geometry-nodes instances, Houdini packed primitives, USD point instancers — because scene scale is otherwise bounded by RAM.

F10Depth

Interchange and the render path are skeletons with correct bones

I/O: OBJ, PLY, STL and glTF 2.0 import/export is solid ground; USD is ASCII-mesh export only, not composition, layers, references or instancing. No FBX (still ubiquitous in game and film pipelines), no Alembic, no STEP/IGES.

Renderer: the architecture is real — deferred scheduler, GBuffer, RenderGraphValidator checking per-pass layout transitions, frame capture, reversed-Z. The shading is not: four shader files totalling 128 lines, and composite.frag computes correct GGX/Smith/Fresnel against two hardcoded light directions and a constant viewDir = (0,0,1), reads no shadow map, and has no IBL, tonemap or anti-aliasing. That is a viewport preview, not a renderer — entirely defensible under foundation-first, but it should be named as such on the roadmap.

Also thin: UV has LSCM (the right algorithm) but no seams, islands or packing — so unwrap produces coordinates no texture pipeline can use yet. Subdivision has fractional creases but no boundary-interpolation rules, no face-varying UV interpolation (textures will swim under subdivision), and no limit-surface evaluation.

§4

Keep it simple — where the code is doing too much

K1Simplify

7,906 lines of hand-written string glue in automation/

The largest non-geometry module in the kernel is a command registry: ~326 string-keyed lambdas over kernel APIs, at roughly 24 lines each, split across AutomationScript.cpp (4,026), AutomationScriptCommands.cpp (3,052) and AutomationScriptUtilities.cpp (828). It is 11% of the kernel, it is stringly-typed so nothing links a command to the API it calls at compile time, and 3,880 of those lines are the only substantial code in the tree with no test reference.

The real cost is not the lines — it is that every future API change has to be hand-mirrored here. That is precisely the kind of tax that makes a 30-year project slow. Blender, Maya and Houdini all embed a scripting language rather than hand-write bindings. Either embed one (Python/Lua) or generate the bindings; keep the batch-harness semantics, which are worth having.

K2Simplify

Header sprawl and pure-façade files

122 public geometry headers include a long tail of one-operation files — NurbsCurveArcLength, NurbsCurveClosestPoint, NurbsCurveFit, NurbsCurveOffset, NurbsCurveSplit, NurbsSurfaceArea, and so on. Each one is a separate public header, a separate manifest entry in the API-freeze fixture, and a separate include for every consumer. Grouping these into NurbsCurveOps / NurbsSurfaceOps loses nothing and shrinks the frozen surface substantially.

Some are pure façades. MeshBoolean (68 lines) exists only to translate its own BooleanOp enum into BooleanOperationType and call BooleanOperation — two public headers and two parallel enums for one operation. Similar near-duplicate pairs worth collapsing or clearly differentiating: MeshSimplify (92) over MeshDecimator (529), MeshVertexMerge (117) beside MeshVertexWeld (227), MeshTopologyAnalysis (79) beside MeshTopologyValidation (211).

K3Simplify

Two names that promise more than the code does

QuadRemesh raycasts a planar resU × resV grid from the bounding box onto the surface through a BVH. That is a shrink-wrapped heightfield: it will produce nonsense for any closed solid or organic shape, and it shares nothing but a name with what the industry means by quad remeshing (QuadriFlow / Instant Meshes — curvature-aligned field guided quadrangulation, which Blender ships). Rename it GridProjectRemesh and the honest capability map improves at zero cost.

ModifierStack's architecture is right — never mutates the base, caches, re-evaluates on demand. But the Modifier struct is one flat record where "only the fields relevant to type are used". That is a fine trade at seven modifier types and a maintenance problem at thirty; it is worth converting to a variant before the stack grows, not after.

K4Simplify

And one place the complexity is earned — leave it alone

The obvious KISS target in this kernel is RobustPredicates: several hundred lines of Knuth/Dekker error-free transformations and expansion arithmetic, to answer "which side of this plane". It is tempting, especially since F1 shows the machinery currently computes nothing the plain double path would not.

Do not simplify it. This is the standard construction — Shewchuk's, as used by CGAL, Triangle and OCCT — the comments correctly note that the intermediate adaptive stages were deliberately omitted to reduce what can be subtly wrong, and it is already written to stay exact if coordinates move to double (F4). The complexity is load-bearing; the build flag is the defect. Simple means "no more parts than the job requires", and exactness is the job.

§5

Documentation that no longer matches the code

CLAUDE.md is the first thing every contributor and agent reads, which makes a wrong line there more expensive than a wrong line of code. Six were wrong at the time of the audit, and the first two were actively dangerous — they instructed new code to use a guard that does not work. All six have since been corrected, along with HANDOFF-CHARTER.md and three parity documents; the table is kept as the record of what drifted and how far.

Worth noting the counter-example, because it is the pattern to keep: Tolerance.h's own header comment says -ffast-math is enabled and therefore inspects IEEE exponent bits directly. That file describes reality and is correct because of it. The geometry module is hardened against NaN today only because it trusted the flag it actually had.

Overall

The foundation is stronger than most projects at this stage in the places that are hardest to retrofit: a typed B-rep with two independent validators, watertight-or-empty as an enforced invariant, a real tolerance model, a seeded fuzz harness, and 121 of 121 geometry sources under test. That discipline — measure it, prove the test is load-bearing, write down the negative results — is the actual asset here, and it is what found F1.

What it is not yet is fast (single-threaded), extensible (no attribute layer), or precise enough for CAD (float coordinates). Those three plus the manifold question are the whole ceiling; everything else on this page is depth that can be added incrementally on a sound base — and the base is sound now that the predicates compute what they claim to. The next decision is not a bug at all: it is whether to commit to an attribute layer and to double precision, both of which get monotonically more expensive with every feature added on top.
